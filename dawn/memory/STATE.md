## At a glance

The memory subsystem is in good shape. LongMemEval (97.0% R@5) and ConvoMem (99.0%) are essentially solved. LoCoMo `recall_generation` lifted three times this cycle: Phase 1 (anchor injection) 0.208 → 0.279, Phase 1.1 (subject-naming prompt fix) 0.279 → 0.371, and Provenance Phase A budget tuning at 12288 → **0.493** on the production-faithful bench (+12.51pp over the Phase 1.1 baseline at production default 3072). Cat-3 multi-hop is *partially* budget-bound — Phase A surfaced a +6.5pp lift at budget=12288, but #5's 24576 probe showed cat-3 plateaus there. The residual cat-3 gap (graph competitors at +20-35pp on reach) likely requires architectural work, but **multi-hop bench questions aren't JARVIS-shape** — the user names entities directly, multi-hop research questions are dataset artifacts — so the cat-3 gap is explicitly subordinated to JARVIS-goal work below. Cross-encoder reranking is **dead** (built, integrated, reverted — see RERANKER_INVESTIGATION.md).

**Phase 1 of Dynamic Context Injection closed 2026-05-09.** Per-turn focus injection composes a ranked + filter-checked + dedup'd block from registered adapters (memory facts/entities/relations/summaries + document chunks + calendar events) and prepends it to the LLM system prompt every user turn. WebUI surfaces the composition via a trust-tiered transcript block + filter-warning chip + score-breakdown popover, all gated behind the existing `body.debug-mode` toggle. Phase 1j.B weight tuning (w_imp 0.2→1.0, w_rec 0.3→0.15) lifted the Component 6 synthetic fix-rate from 7/11 to 11/11 on all three judge providers. Manual smoke against the developer's real DB initially showed stale-extraction artifacts (meta-facts, duplicate "Jon"/"Jonathan Smith" entities) — root-caused to derived-state cruft from before April 2026 quality improvements, NOT the focus injection itself. The new `dawn-admin memory reextract` admin command resolved this by dropping derived tables + recovery-worker re-extraction under the current pipeline; live-validated 272 convs / 3052 msgs / ~$1 spend, after which real-DB family + stock queries surface the right facts cleanly. The reextract utility is **permanent infrastructure** for any future major memory-subsystem upgrade that requires re-deriving from conversation history.

**Steps 1-3 of summary retrieval closed 2026-05-11.** The summary adapter shipped under Phase 1 was keyword-only — empirical observation across an 8-turn Mother's Day conversation showed **zero summaries surfacing** in per-turn injection because LIKE-pattern matching on the long natural-language query rarely landed on stored summary text. Step 1 extended the extraction prompt from "1-2 sentence" to "3-5 sentences, ~1500 chars covering topics / key parameters / decisions / outcomes" so summaries become the timeline-of-record (new summaries land ~850 chars vs the old ~287 p90). Step 2 shipped `dawn-admin memory summarize-missing` to backfill summary rows for conversations whose original extraction never produced one. Step 3 added schema v45 `memory_summaries.embedding BLOB` + hybrid keyword+semantic search in `summary_adapter_query` (merge by id, max-score wins, keyword floor 0.4) + embed-at-create wired in both live extraction and the backfill worker + recompute worker extended with a summaries pass. v46 nulled `users.embeddings_model_id` so the recompute worker treated every user as stale and backfilled the v45 column on next boot — all 283 historical summaries gained embeddings without manual intervention. Default tuning surfaced two clearly-broken pre-Step-3 values: `top_k = 8` (was filling every slot with facts and starving everything else) bumped to 12, `source_weights.memory_summary = 0.7` (was a pre-adapter guess that kept summaries out of top-K entirely) bumped to 1.0. `weight_recency` initially left at the Phase 1j-validated 0.15 with a 0.3 tension documented in `config_defaults.c` and `dawn.toml.example` for re-bench (which subsequently shipped 2026-05-13 and promoted 0.15 → 0.30 — see Recently shipped row). Live-validated end-to-end: GPU-strategy query with zero keyword overlap ("how am I approaching graphics hardware purchases?") surfaced the right GPU summaries via pure cosine; "what colors are in a sunset?" correctly declined confabulation; Mother's Day query that previously double-dipped now answers from the focus block alone. The double-dip mitigation in the focus-block framing tells the LLM the memory tool isn't needed when the block has the answer AND to fall through to the tool without asking when it doesn't — closes the redundant-search-call gap that was burning ~300-500 tokens per memory-flavored turn. **Step 4** (full re-extract under the new prompt) remains queued as the canonical cleanup pass for legacy paraphrase-ladder facts + interaction-event meta-facts (Mother's Day query still shows 5/10 facts as legacy "User's mother's birthday is February 16th" × 3 noise — Step 4 fixes via the new paraphrase gate + meta-fact prompt rule).

**Entity-merge Phase 1 + Phase 1.5 + three fold-ins closed 2026-05-09 → 2026-05-10.** The dev's "Jon" / "Jonathan Smith" / "user" duplication problem is resolved through equivalence-class soft-merge: a canonical entity owns the relations + facts and aliases soft-link to it via `canonical_id`. Phase 1 shipped the schema (v43: `canonical_id` self-FK + `is_user_self` UNIQUE partial index + audit-log + merge-proposal staging + 5 partial indexes) and the six-stage resolver cascade with composite scoring (0.30 jaccard + 0.30 cosine + 0.25 exclusive-relation overlap + 0.10 contact-field overlap + 0.05 type + ±0.10/0.20 substring/user-self bonuses). Phase 1.5 (schema v44) added `users.real_name` / `users.preferred_address` / `users.identity_aliases` so the synthetic-self path stops borrowing `persona_description` for identity, plus directional Jaccard for short-name candidates against verbose synthetic, a `user`-token allow-list, and a real-name-required gate. Three fold-ins followed live-testing: (#1 alias-substring bonus + report sort, #2 promote-existing-match path replacing the always-INSERT seed, #3 commit-mode focused scoring against the user-self specifically). Live Path A validation: `Jonathan Smith` (1406) promoted to `is_user_self=1`, `Jon` (1230) auto-merged via review-band approval, `user` (1162) operator-merged through the WebUI. Operator surface: `dawn-admin memory entity {merge,split,aliases,history,list,link-user-self}` + WebUI Graph-tab Suggested-Merges panel. Phase 2 (auto-merge gate at extraction time + threshold calibration) is the next step on this workstream.

Two attempts (prompt-additive in attempt #1, structural JSON reframe via cγ in attempt #2) both moved the probe but neither moved full-LoCoMo aggregate generation. Quantified probe-vs-bench gap for this class of fix: +25pp probe c3 lift → ~0pp full bench. The mechanism (LLM defaults subject=role:user) is real and probe-detectable, but is dominated by retrieval / top-K dynamics in full-conv extraction. Permanent infrastructure shipped: multi-model + 2-of-3 quorum probe + Component 3 fix-rate mini-bench. Production `memory_extraction.c` unchanged.

Short-term backlog is empty. The medium-term roadmap (priority-ordered for the JARVIS goal) is now reordered around the bench evidence: **dynamic context injection → multi-language injection filter → speaker mis-attribution (deferred, lower priority)**.  The "I don't remember" gate shipped 2026-05-13 — search-score-floor against marginal-cosine fabrication, default-on at both the memory.search tool and the per-turn focus adapter.

Diagnostic profiling (`/tmp/profile_cat2.py`) on the same smoke baseline: cat-2 wrong cases (n=22), gold answer location: **NOT_PRESENT 19/22 (86%)** · FACTS 1 · SUMMARIES 2 · SOURCE 0. **Only 4/63 (6.3%) cat-2 questions have a temporal anchor in the query at all** — most are "When did X happen?" shapes the parser cannot extract a window from (the answer IS the temporal info, not the query). Theoretical max lift from parser expansion: **+3/63 = +4.8pp cat-2, +1.3pp overall**, assuming a perfect parser change fixes all 3 ranking-issue cases without regression. Original estimate (+3-5pp overall, +10-20pp cat-2) was hand-waved, not data-grounded. Real ceiling is ~1pp and the addressable surface is small.
3. **Selective question decomposition — abandoned by same diagnosis**. Cat-3 + cat-4 failure modes are dominated by NOT_PRESENT in the same proportion. The Phase 1A entity-graph 1-hop expansion already covers most multi-hop signal; query decomposition fires on ~20-30% of queries but cannot invent missing facts. Bigger architectural change, higher risk, same ~1-3pp ceiling (matching #1+#2 scale).

**Big-picture diagnosis (this session's empirical finding):** The dominant failure mode across all categories is **52.8% NOT_PRESENT** — answers that never made it into any memory_text section. That's an **extraction recall** problem (Phase 4.5 territory), not a memory_text-shape problem (candidate #1) or a query-parser problem (candidate #2) or a retrieval-ranking problem (candidate #3). The three candidates were lined up assuming we knew where the gap lived; the data says we didn't. Memory subsystem is called **done for now** at the 0.7324 leader-comparable baseline.

**If memory work resumes**, the only candidate on the list that addresses NOT_PRESENT is **Phase 4.5 — per-turn extraction** (see `dawn/docs/TODO.md`). Filed as "untested, decision-pending; likely dead-letter without testing" — but it's the only entry in the queue that targets the diagnosed bottleneck. Test protocol + gates already in the TODO entry.

**Out / dead-letter pile** (literature-deprioritized OR bench-deprioritized — keep visible so we don't re-propose):
- **Cross-encoder reranker as primary lever** — OMEGA explicitly *removed* their cross-encoder; MemReranker beats `bge-reranker-v2-m3` by only +4.4 MAP retrieval. Dominant-token heuristic already shipped 2026-05-13.
- **Per-question-type generation prompts** — agent research synthesis showed leaders use uniform templates. Breaks leader-comparable protocol.
- **Deeper entity-graph traversal (2+ hops)** — literature sharply against unbounded traversal; 1-2 hops is the empirical sweet spot.
- **Side-mention completeness extraction rule** — bench-validated regressive (-0.78pp net, cat-3 -6.5pp specifically).
- **Mem0 Phase 2 scoring composition (weight shift, over-fetch, spread-attenuated entity boost)** — Phase 2A weight shift 0.30/0.70 → 0.40/0.60 bench-validated as the regressor (-0.72pp). 2B over-fetch neutral. 2C spread-attenuated entity boost structurally redundant with DAWN's existing entity-graph 1-hop retrieval. All three reverted in full; no code carried. The hypothesis "BM25 makes keyword channel competitive, so soften semantic dominance" didn't hold for DAWN's bench.
- **Mem0 no-echo extraction rule (Phase 3 D)** — bench-validated as over-aggressive against DAWN's existing provenance + source-excerpt machinery; full Phase 3 with 3D ON regressed cat-4 -2.4pp; surgical revision removed 3D and the regression disappeared. - **RRF parallel-channel retrieval** — re-tested post-Phase 1 (the trigger condition from MEM0_ARCHITECTURAL_PARITY.md). Result -0.58pp on Phase 3 baseline (0.7324 → 0.7266), same direction as original May 2026 -3.7pp regression. The hypothesis "BM25 made channels balanced, so RRF over balanced channels might lift" didn't hold. Code stays behind `rrf_enabled` flag (default off); formally dead-letter per parity plan stopping criteria — don't carry as "experimental, may re-enable".
- **Phase 4.5 — per-turn extraction** (dev's idea, not from Mem0) — extracted from the sealed parity doc to `dawn/docs/TODO.md` (living doc) on 2026-05-17 as active workstream tracking. The original trigger note said "if Phase 3 closes most of the forest-vs-trees gap, per-turn may end up dead-lettering naturally" — and Phase 3 cat-1 +2.5pp gen lift DID target that same concrete-fact gap. Also has real infrastructure cost (extraction fires on every conversation turn instead of session-end → ~10-100x extraction LLM cost during live use). Plausibly already dead-lettered without bench, but a legitimate decision point if production telemetry surfaces missing-trees patterns. **As of 2026-05-17 evening this is now the ONLY queued candidate that addresses the diagnosed NOT_PRESENT bottleneck** — every other candidate (memory_text shape, temporal parser, question decomposition) was empirically shown to target the wrong failure mode. Full design + test protocol + gates in the TODO entry.
- **Memory_text shape rebuild (Step A)** — CLOSED 2026-05-17 evening. Bench-validated REGRESSIVE −1.3pp on 231-QA smoke. Diagnostic profiling: only 7.8% of QAs have answers in summaries (the only section Step A affects), answer-bearing content sits at char 500-900 (median 606, p95 871), so any cap aggressive enough to save meaningful bytes (≤700) systematically loses the answer. cap=1000 preserves 100% of answer-bearing content but saves only ~10% bytes. No operating point delivers compression without signal loss. Code deleted in same session — no flag, no helper, no gate retained. Don't re-propose under the same framing.
- **Hard temporal filter parser expansion** — CLOSED 2026-05-17 evening, BEFORE writing code. Cat-2 86% of wrong cases (19/22) have answer NOT_PRESENT — extraction gap, parser can't help. Only 4/63 cat-2 questions have a temporal anchor in the query at all (most are "When did X" shapes with no extractable window). Don't re-propose unless cat-2 question shape mix changes materially.
- **Selective question decomposition (candidate #3)** — CLOSED 2026-05-17 evening, BEFORE writing code. Same NOT_PRESENT-dominated diagnosis as #1 and #2; the entity-graph 1-hop expansion already covers most addressable multi-hop signal; bigger architectural change for same ~1-3pp ceiling. Park unless production telemetry surfaces a query-shape pattern decomposition specifically unlocks.

**Memory work is called done for now at the 0.7324 leader-comparable baseline.** The diagnosed bottleneck (52.8% NOT_PRESENT across all categories) is an extraction-recall problem that none of the three queued retrieval-side candidates was attacking. Phase 4.5 per-turn extraction remains the only candidate that targets that surface; revisit when there's appetite for the runtime LLM cost trade-off.**

## Long-term direction (architectural / strategic)

These items are deliberately deprioritized below the JARVIS-goal medium-term workstreams above. They remain on the roadmap but are not next.

1. **Relation-aware retrieval (graph traversal at query time)** — open option, not a commitment. Phase A established cat-3 IS partially budget-bound (+6.5pp at budget=12288), and #5's 24576 probe established cat-3 plateaus there — the residual gap (graph competitors at +20-35pp on reach) genuinely needs architectural work to close. BUT: multi-hop bench questions aren't JARVIS-shape (the user names entities directly; multi-hop research questions are dataset artifacts). Subordinate to dynamic context injection + speaker mis-attribution work. Substantial architectural shift; weeks of work. Re-evaluate after JARVIS-shape work lands and we have evidence on whether multi-hop user queries actually exist in production. See LOCOMO_CAT3_PROFILING.md.

2. **Standalone memory/retrieval library** — *re-framed as domain-agnostic structured-memory infrastructure*. Extract `embedding_engine` + `memory_db` + `document_db` + similarity into `libdawn_memory.so` + Python bindings. The same infrastructure that builds JARVIS for one user works for any structured-knowledge corpus — codebase, medical literature, legal codes, internal docs. Personal AI memory and domain-knowledge LLM augmentation are the same architectural problem viewed from two angles. Unlocks: MCP server for the coding assistant (TODO Coding Assistant section), domain-specific memory instances, external benchmarking. ~1-2 weeks for v1. Composes with provenance work that already shipped.

3. **Cross-encoder reranking** — **dead.** Don't revisit. Investigation already happened, no net benefit on conversational data.

4. **RRF parallel-channel retrieval** — **dead** (formally dead-lettered 2026-05-17 after Phase 4A re-test). Originally regressed -3.7pp in May 2026; re-tested post-Phase-1 BM25 + Phase-3 specificity per the parity plan's "BM25 balances channels" trigger condition and still regressed -0.58pp. Code stays behind `rrf_enabled` flag (default off) but the doc-level decision is: don't carry as "experimental, may re-enable". Don't propose another re-test without a fundamentally different motivation than channel rebalancing.

5. **Mem0 spread-attenuated entity boost** — **dead** (deleted 2026-05-17). Briefly added then removed during Phase 2C — structurally redundant with DAWN's entity-graph 1-hop retrieval (Phase 1A, May 13), which achieves the same "cap high-degree entities from dominating" goal via per-seed fan-out budget + dedup. Apache 2.0 attribution removed from NOTICE in same session.
