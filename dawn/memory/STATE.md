The assistant feels like it knows the user, anticipates relevant context as the conversation shifts, never confabulates, never says "let me search my files." Trust is the substrate; benchmark scores serve that goal, they don't define it. When in doubt, prioritize work that strengthens the JARVIS-shape behavior over work that closes a bench gap that doesn't.

## At a glance

The memory subsystem is in good shape. LongMemEval (97.0% R@5) and ConvoMem (99.0%) are essentially solved. LoCoMo `recall_generation` lifted three times this cycle: Phase 1 (anchor injection) 0.208 → 0.279, Phase 1.1 (subject-naming prompt fix) 0.279 → 0.371, and Provenance Phase A budget tuning at 12288 → **0.493** on the production-faithful bench (+12.51pp over the Phase 1.1 baseline at production default 3072). Cat-3 multi-hop is *partially* budget-bound — Phase A surfaced a +6.5pp lift at budget=12288, but #5's 24576 probe showed cat-3 plateaus there. The residual cat-3 gap (graph competitors at +20-35pp on reach) likely requires architectural work, but **multi-hop bench questions aren't JARVIS-shape** — the user names entities directly, multi-hop research questions are dataset artifacts — so the cat-3 gap is explicitly subordinated to JARVIS-goal work below. Cross-encoder reranking is **dead** (built, integrated, reverted — see RERANKER_INVESTIGATION.md).

**Phase 1 of Dynamic Context Injection closed 2026-05-09.** Per-turn focus injection composes a ranked + filter-checked + dedup'd block from registered adapters (memory facts/entities/relations/summaries + document chunks + calendar events) and prepends it to the LLM system prompt every user turn. WebUI surfaces the composition via a trust-tiered transcript block + filter-warning chip + score-breakdown popover, all gated behind the existing `body.debug-mode` toggle. Phase 1j.B weight tuning (w_imp 0.2→1.0, w_rec 0.3→0.15) lifted the Component 6 synthetic fix-rate from 7/11 to 11/11 on all three judge providers. Manual smoke against the developer's real DB initially showed stale-extraction artifacts (meta-facts, duplicate "Kris"/"Kristopher Kersey" entities) — root-caused to derived-state cruft from before April 2026 quality improvements, NOT the focus injection itself. The new `dawn-admin memory reextract` admin command resolved this by dropping derived tables + recovery-worker re-extraction under the current pipeline; live-validated 272 convs / 3052 msgs / ~$1 spend, after which real-DB family + stock queries surface the right facts cleanly. The reextract utility is **permanent infrastructure** for any future major memory-subsystem upgrade that requires re-deriving from conversation history.

**Steps 1-3 of summary retrieval closed 2026-05-11.** The summary adapter shipped under Phase 1 was keyword-only — empirical observation across an 8-turn Mother's Day conversation showed **zero summaries surfacing** in per-turn injection because LIKE-pattern matching on the long natural-language query rarely landed on stored summary text. Step 1 extended the extraction prompt from "1-2 sentence" to "3-5 sentences, ~1500 chars covering topics / key parameters / decisions / outcomes" so summaries become the timeline-of-record (new summaries land ~850 chars vs the old ~287 p90). Step 2 shipped `dawn-admin memory summarize-missing` to backfill summary rows for conversations whose original extraction never produced one. Step 3 added schema v45 `memory_summaries.embedding BLOB` + hybrid keyword+semantic search in `summary_adapter_query` (merge by id, max-score wins, keyword floor 0.4) + embed-at-create wired in both live extraction and the backfill worker + recompute worker extended with a summaries pass. v46 nulled `users.embeddings_model_id` so the recompute worker treated every user as stale and backfilled the v45 column on next boot — all 283 historical summaries gained embeddings without manual intervention. Default tuning surfaced two clearly-broken pre-Step-3 values: `top_k = 8` (was filling every slot with facts and starving everything else) bumped to 12, `source_weights.memory_summary = 0.7` (was a pre-adapter guess that kept summaries out of top-K entirely) bumped to 1.0. `weight_recency` left at the Phase 1j-validated 0.15 with the 0.3 tension documented in both `config_defaults.c` and `dawn.toml.example` for re-bench once Phase 1j gains a summary-relevant probe. Live-validated end-to-end: GPU-strategy query with zero keyword overlap ("how am I approaching graphics hardware purchases?") surfaced the right GPU summaries via pure cosine; "what colors are in a sunset?" correctly declined confabulation; Mother's Day query that previously double-dipped now answers from the focus block alone. The double-dip mitigation in the focus-block framing tells the LLM the memory tool isn't needed when the block has the answer AND to fall through to the tool without asking when it doesn't — closes the redundant-search-call gap that was burning ~300-500 tokens per memory-flavored turn. **Step 4** (full re-extract under the new prompt) remains queued as the canonical cleanup pass for legacy paraphrase-ladder facts + interaction-event meta-facts (Mother's Day query still shows 5/10 facts as legacy "User's mother's birthday is February 16th" × 3 noise — Step 4 fixes via the new paraphrase gate + meta-fact prompt rule).

**Entity-merge Phase 1 + Phase 1.5 + three fold-ins closed 2026-05-09 → 2026-05-10.** The dev's "Kris" / "Kristopher Kersey" / "user" duplication problem is resolved through equivalence-class soft-merge: a canonical entity owns the relations + facts and aliases soft-link to it via `canonical_id`. Phase 1 shipped the schema (v43: `canonical_id` self-FK + `is_user_self` UNIQUE partial index + audit-log + merge-proposal staging + 5 partial indexes) and the six-stage resolver cascade with composite scoring (0.30 jaccard + 0.30 cosine + 0.25 exclusive-relation overlap + 0.10 contact-field overlap + 0.05 type + ±0.10/0.20 substring/user-self bonuses). Phase 1.5 (schema v44) added `users.real_name` / `users.preferred_address` / `users.identity_aliases` so the synthetic-self path stops borrowing `persona_description` for identity, plus directional Jaccard for short-name candidates against verbose synthetic, a `user`-token allow-list, and a real-name-required gate. Three fold-ins followed live-testing: (#1 alias-substring bonus + report sort, #2 promote-existing-match path replacing the always-INSERT seed, #3 commit-mode focused scoring against the user-self specifically). Live Path A validation: `Kristopher Kersey` (1406) promoted to `is_user_self=1`, `Kris` (1230) auto-merged via review-band approval, `user` (1162) operator-merged through the WebUI. Operator surface: `dawn-admin memory entity {merge,split,aliases,history,list,link-user-self}` + WebUI Graph-tab Suggested-Merges panel. Phase 2 (auto-merge gate at extraction time + threshold calibration) is the next step on this workstream.

Speaker mis-attribution attempt #2 closed 2026-05-08 with no production ship. Two attempts (prompt-additive in attempt #1, structural JSON reframe via cγ in attempt #2) both moved the probe but neither moved full-LoCoMo aggregate generation. Quantified probe-vs-bench gap for this class of fix: +25pp probe c3 lift → ~0pp full bench. The mechanism (LLM defaults subject=role:user) is real and probe-detectable, but is dominated by retrieval / top-K dynamics in full-conv extraction. Permanent infrastructure shipped: multi-model + 2-of-3 quorum probe + Component 3 fix-rate mini-bench. Production `memory_extraction.c` unchanged.

Short-term backlog is empty. The medium-term roadmap (priority-ordered for the JARVIS goal) is now reordered around the bench evidence: **dynamic context injection → multi-language injection filter → "I don't remember" gate → speaker mis-attribution (deferred, lower priority)**.

## Long-term direction (architectural / strategic)

These items are deliberately deprioritized below the JARVIS-goal medium-term workstreams above. They remain on the roadmap but are not next.

1. **Relation-aware retrieval (graph traversal at query time)** — open option, not a commitment. Phase A established cat-3 IS partially budget-bound (+6.5pp at budget=12288), and #5's 24576 probe established cat-3 plateaus there — the residual gap (graph competitors at +20-35pp on reach) genuinely needs architectural work to close. BUT: multi-hop bench questions aren't JARVIS-shape (the user names entities directly; multi-hop research questions are dataset artifacts). Subordinate to dynamic context injection + speaker mis-attribution work. Substantial architectural shift; weeks of work. Re-evaluate after JARVIS-shape work lands and we have evidence on whether multi-hop user queries actually exist in production. See LOCOMO_CAT3_PROFILING.md.

2. **Standalone memory/retrieval library** — *re-framed as domain-agnostic structured-memory infrastructure*. Extract `embedding_engine` + `memory_db` + `document_db` + similarity into `libdawn_memory.so` + Python bindings. The same infrastructure that builds JARVIS for one user works for any structured-knowledge corpus — codebase, medical literature, legal codes, internal docs. Personal AI memory and domain-knowledge LLM augmentation are the same architectural problem viewed from two angles. Unlocks: MCP server for the coding assistant (TODO Coding Assistant section), domain-specific memory instances, external benchmarking. ~1-2 weeks for v1. Composes with provenance work that already shipped.

3. **Cross-encoder reranking** — **dead.** Don't revisit. Investigation already happened, no net benefit on conversational data.
