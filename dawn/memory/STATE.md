# Memory Subsystem — Current State

**Purpose:** living snapshot of where the memory subsystem stands. Read this at the start of any memory-focused work session before diving into individual atlas docs or `dawn/docs/TODO.md`. Refresh when a major shipment lands.

**North star:** JARVIS/FRIDAY minus sci-fi. The assistant feels like it knows the user, anticipates relevant context as the conversation shifts, never confabulates, never says "let me search my files." Trust is the substrate; benchmark scores serve that goal, they don't define it. When in doubt, prioritize work that strengthens the JARVIS-shape behavior over work that closes a bench gap that doesn't.

## At a glance

The memory subsystem is in good shape. LongMemEval (97.0% R@5) and ConvoMem (99.0%) are essentially solved. LoCoMo `recall_generation` lifted three times this cycle: Phase 1 (anchor injection) 0.208 → 0.279, Phase 1.1 (subject-naming prompt fix) 0.279 → 0.371, and Provenance Phase A budget tuning at 12288 → **0.493** on the production-faithful bench (+12.51pp over the Phase 1.1 baseline at production default 3072). The residual cat-3 gap (graph competitors at +20-35pp on reach) likely requires architectural work, but **multi-hop bench questions aren't JARVIS-shape** — the user names entities directly, multi-hop research questions are dataset artifacts — so the cat-3 gap is explicitly subordinated to JARVIS-goal work below. Cross-encoder reranking is **dead** (built, integrated, reverted — see RERANKER_INVESTIGATION.md).

Speaker mis-attribution attempt #2 closed 2026-05-08 with no production ship. Two attempts (prompt-additive in attempt #1, structural JSON reframe via cγ in attempt #2) both moved the probe but neither moved full-LoCoMo aggregate generation. Quantified probe-vs-bench gap for this class of fix: +25pp probe c3 lift → ~0pp full bench. The mechanism (LLM defaults subject=role:user) is real and probe-detectable, but is dominated by retrieval / top-K dynamics in full-conv extraction. Permanent infrastructure shipped: multi-model + 2-of-3 quorum probe + Component 3 fix-rate mini-bench. Production `memory_extraction.c` unchanged.

Short-term backlog is empty. The medium-term roadmap (priority-ordered for the JARVIS goal) is now reordered around the bench evidence: **dynamic context injection → multi-language injection filter → "I don't remember" gate → speaker mis-attribution (deferred, lower priority)**.

## Long-term direction (architectural / strategic)

These items are deliberately deprioritized below the JARVIS-goal medium-term workstreams above. They remain on the roadmap but are not next.

1. **Relation-aware retrieval (graph traversal at query time)** — open option, not a commitment. Phase A established cat-3 IS partially budget-bound (+6.5pp at budget=12288), and #5's 24576 probe established cat-3 plateaus there — the residual gap (graph competitors at +20-35pp on reach) genuinely needs architectural work to close. BUT: multi-hop bench questions aren't JARVIS-shape (the user names entities directly; multi-hop research questions are dataset artifacts). Subordinate to dynamic context injection + speaker mis-attribution work. Substantial architectural shift; weeks of work. Re-evaluate after JARVIS-shape work lands and we have evidence on whether multi-hop user queries actually exist in production. See LOCOMO_CAT3_PROFILING.md.

2. **Standalone memory/retrieval library** — *re-framed as domain-agnostic structured-memory infrastructure*. Extract `embedding_engine` + `memory_db` + `document_db` + similarity into `libdawn_memory.so` + Python bindings. The same infrastructure that builds JARVIS for one user works for any structured-knowledge corpus — codebase, medical literature, legal codes, internal docs. Personal AI memory and domain-knowledge LLM augmentation are the same architectural problem viewed from two angles.
